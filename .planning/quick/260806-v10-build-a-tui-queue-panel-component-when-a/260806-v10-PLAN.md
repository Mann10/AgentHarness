<objective>
Build the TUI "Queue" panel: when a second prompt is submitted while a turn is still running, the Scheduler FIFO backlog grows and a bordered panel appears above the input bar showing the next queued prompt text (truncated) plus a count of additional queued prompts. The panel mirrors backend state over RPC via a new `backlog_changed` notification and disappears when the backlog drains to zero.

Purpose: the TUI currently only tracks a local `busy` flag and has zero visibility into the real backlog (`harness/scheduler.py` `_backlog: asyncio.Queue`, `backlog_size` property). This feature surfaces that real state.
Output: backend event emission (enqueue/drain/cancel) → RPC notification → TUI store slice → Queue panel component, plus focused Python tests.
</objective>

## Design Decisions (locked from CONTEXT.md + documented discretion)

1. **Backend-driven (LOCKED D-1):** a `backlog_changed` event notification is the single source of truth. No TUI-local queue. No pollable method needed — the existing event-forwarding pipeline (D-08/D-09) is the cleanest fit.
2. **Payload contract (D-06 style):** `{depth: int, next_prompt: str}` ONLY. `session_id` rides on the notification `request_id` (matches `skill_loaded`; NOT duplicated in payload). `next_prompt` is the full prompt text; truncation is a TUI-presentation concern.
3. **Queue-head peek:** `asyncio.Queue` cannot peek. Add a parallel `collections.deque[str]` mirror in the Scheduler. Every queue mutation is immediately followed by the mirror mutation in the same synchronous block (no `await` between) → no event-loop interleaving → mirror never drifts.
4. **Emission points:** (a) enqueue — after `put`+`append` succeeds in `submit_prompt`; (b) drain — after `get_nowait`+`popleft` in `_run_turn`, before spawning the next turn task (covers drain-to-zero: depth=0 hides the panel); (c) cancel — after the cancellation wait, clear the backlog and emit depth=0 unconditionally.
5. **Cancel clears the backlog (documented decision):** queued prompts under a cancelled turn never execute (existing behavior — the drain never runs on a cancelled task, orphaning them). Clearing on cancel keeps the panel truthful and matches user intent of "stop". Existing `test_cancel_stops_current_turn` does not assert backlog, so no regression. `shutdown()`'s "does not drain" comment refers to *processing*, which stays true.
6. **Session switch (WR-05 pattern):** events carry session via request_id; the TUI applies `params.request_id === state.activeSessionId` before `setBacklog`, and the store resets `queue` to `{depth: 0, nextPrompt: ""}` inside `setActiveSession` so a stale panel never lingers for the new session.
7. **Copy (discretion):** the panel is already titled "Queue" (bordered header), so the body is `"<next prompt>" (+N more waiting)` — the LOCKED `QUEUE:` prefix from the user's inline example is redundant inside a titled panel. depth === 1 renders just the quoted prompt (no suffix); N = depth − 1.
8. **Out of scope (pre-existing):** a turn that raises a non-cancelled exception leaves the backlog untouched (same orphan behavior as today). Not changed here — the panel mirrors real queue contents, which is truthful.

# Quick task 260806-v10: TUI Queue Panel for Backlogged Prompts - Context

**Gathered:** 2026-08-06
**Status:** Ready for planning

<domain>
## task Boundary

Build another component for the TUI for queuing message rendering. When the user sends a first prompt and it is still running, and then sends a second prompt while the first is still going, the TUI should show a panel above the input prompt indicating the queued prompt (e.g. `QUEUE: next prompt`). Once the initial turn completes, the panel goes away and normal flow continues.

Backend reality: the Scheduler already maintains a real FIFO backlog (`harness/scheduler.py` `_backlog: asyncio.Queue`, `backlog_size` property). The TUI currently has no visibility into that backlog — it only tracks a local `busy` flag.

</domain>

<decisions>
## Implementation Decisions

### Queue data source (LOCKED: Backend-driven)
- Add a small backend RPC surface so the panel mirrors the real Scheduler FIFO state — e.g. a `backlog_changed` event notification carrying queue depth (and next prompt), and/or a `scheduler.status` method the TUI can query/sync with.
- TUI must NOT track the queue locally (no drift): the panel reflects actual backend backlog.
- Prompt text is available on the backend (the queued prompt string is in the Scheduler backlog).

### Panel content (LOCKED: Prompt text + count)
- Panel shows the next queued prompt text (truncated to row width) plus a count of additional queued prompts, e.g. `QUEUE: "fix the bug" (+2 more waiting)`.
- When only one prompt is queued, show it without a "+N" suffix (or with a natural "1 waiting" phrasing).
- The panel disappears when the backlog drains to zero.

### Panel style (LOCKED: Full panel like others)
- A bordered panel with a title (`Queue`) in the same visual style as the Conversation and ToolMonitor panels (single border, header line, consistent with `conversation-panel.tsx` / `tool-monitor-panel.tsx` conventions).
- Rendered above the input bar in the app layout (`app.tsx`).
- Follows existing TUI component conventions (zustand store slice + ink component).

### OpenCode's Discretion
- Exact RPC design choice (event notification vs pollable method vs both) — pick the cleanest that matches the existing RPC protocol patterns (typed `event` notifications forwarded via `RPCServer`).
- Exact truncation width / copy wording.
- Store field naming and component file placement under `tui-ink/src/components/`.

</decisions>

<specifics>
## Specific Ideas

- Example from user: show "QUEUE: next prompt" above the input while turn 1 runs; clear when turn 1 completes and turn 2 starts.
- The Scheduler already emits no queue-related events today; adding one is a new notification type following the D-08/D-09 pattern (type string + payload extractor in `server.py`).
- TUI store currently has `busy`, `status`, `conversation`; a `queue` slice (depth + next prompt) fits the zustand store pattern.
- Existing event wiring: `harness/events.py` dataclasses, `server.py` `_DOMAIN_TO_NOTIFICATION` map + `_PAYLOAD_EXTRACTORS`, `rpc-client.ts` `handleEvent` switch. Any new event must be threaded through all four + `types.ts`.

</specifics>

# Phase 16 — TUI Integration (Skill Indicator): UI Design Contract

> Visual and interaction contract for the Ink TUI (`tui-ink/`) changes in Phase 16.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> **This is a TERMINAL UI (Ink 7.1 + React 19).** All units are **character cells**, not px. There is no font-size control, no line-height beyond 1, and no CSS. Styling is exclusively Ink props on `<Box>`/`<Text>` (`color`, `bold`, `dimColor`, `italic`, `underline`, `reverse`, `borderStyle`, `borderColor`). The web-oriented template sections below are adapted accordingly.

**Extends:** 09-UI-SPEC.md (base design system: philosophy §1, color §2, icons §6, keyboard §4) and 11-UI-SPEC.md (terminal-adapted contract format, footer hints §6.5, `addNotice`/message patterns, module-local token convention §10).
**Consumes:** Phase 15's `skills.load` RPC ack `{ skill, status: loaded|already_loaded|not_found }` (15-CONTEXT D-05/D-06), `loadSkill()` on `rpc-client.ts:140`, `SkillLoadResult`/`SkillLoadStatus` in `types.ts`, and the shared backend `load_skill()` path (`runtime.py:178`).
**Out of visual scope (noted for the executor, NOT contract-controlled):** the typed `skill_loaded` notification plumbing across the five backend touchpoints (harness event → server mapping + extractor → `NotificationType` → `handleEvent` → store). The store-side `loadedSkills` state IS contract-controlled because the footer chip consumes it.

---

## 1. Design Philosophy & Principles

Carried forward from 09-UI-SPEC §1 (terminal-first, content-maximal, keyboard-first, minimal chrome, streaming-native, no component library) and 11-UI-SPEC §1 (honest discoverability, no chrome on every row, redraw on events), plus:

| Principle | Implication |
|-----------|-------------|
| **Persistent state lives in chrome, transient feedback lives in the stream** | Loaded skills are session-scoped state (ACT-05) → persistent footer chip. `/skill` outcomes are one-shot feedback → inline notices via the existing `notice` message role. The chip and the notices never overlap: the chip reflects the `skill_loaded` **notification**; the notices reflect the `skills.load` **RPC ack**. |
| **Transparency by default** | The chip shows EVERY loaded skill name (D-03), because every loaded body stays in context for the session and Phase 17 combines their `allowed-tools` via intersection. Truncation (many skills / narrow terminal) must keep the hidden count visible — never silently drop names. |
| **Mirror the REPL, word for word** | The three inline notices reuse the exact REPL ack strings (16-CONTEXT D-04). One dedup contract, two entry points, identical output copy. |
| **No new semantic color meanings** | The chip uses only weight + existing `$text`/`$text-muted` tokens. The notice tones reuse the existing success (`green`) and error (`red`) meanings. `$accent` blue stays picker-exclusive (11-UI-SPEC §5). |
| **Slash commands are local and immediate** | `/skill` is intercepted like `/session`/`/new` (16-CONTEXT D-05): exact-match, handled inline, input cleared, **never** falls through to `submitPrompt`. |

**Terminal grid units (1 unit = 1 character cell).** The 09/11 cell scale is unchanged; Phase 16 adds one row to the footer.

| Token | Cells | Usage |
|-------|-------|-------|

## 4. Typography

Terminal font, one size, line-height fixed at 1. Declared **weights (exactly 2: regular, bold)** and **attributes (exactly 4: bold, dimColor, italic, underline)** — unchanged from 11-UI-SPEC §4. Phase 16 adds **three notice tones** that extend the existing `notice` role's styling (still 1 weight + 1 attribute per tone):

| Role | Weight | Attribute | Color | Usage |
|------|--------|-----------|-------|-------|
| Body | regular | — | `$text` (white) | Message content, footer hint items (unchanged) |
| Emphatic | **bold** | — | `$text` (white) | **Chip skill names** (the only new emphatic usage this phase) |
| Muted | regular | `dimColor` | — | **Chip `Skill:` label**, footer hints, metadata (unchanged) |
| Subtle | regular | `italic` | `dimColor` | **Notice tone `info`** — `already loaded`, `Usage:` line (existing notice style, unchanged) |
| Success tone | **bold** | — | `$primary` (green) | **Notice tone `success`** — `Loaded skill <name>` with `✓` prefix |
| Error tone | **bold** | — | `$error` (red) | **Notice tone `error`** — `Skill '<name>' not found` with `✗` prefix |

Rules (unchanged): `italic` is never the only signal — it pairs with `dimColor` and is reserved for passive/informational lines; `underline` remains panel-titles-only; no `reverse`. Every color signal pairs with a symbol (`✓`/`✗`) or weight (bold names).

Carried forward from 09-UI-SPEC §2 / 11-UI-SPEC §5, normalized to the live code vocabulary. **No new tokens are introduced.** The chip uses weight + `$text` only; the notice tones reuse the existing `$primary`/`$error` meanings.

### 60 / 30 / 10 split

| Token | Ink Value | Live Usage Today | Phase 16 Usage |
|-------|-----------|------------------|----------------|
| `$background` | `#1a1a1a` | App background | unchanged |
| `$surface` | `#222222` | Panel/assistant bg | unchanged |
| `$panel` | `#2a2a2a` | Border/dividers | unchanged |
| `$text` | `white` | Primary content | **+ chip skill names (bold)** |
| `$text-muted` | `dimColor` | Metadata, labels | **+ chip `Skill:` label, `+N more` suffix** |
| `$primary` | `green` | Success + focus border, `●` active, `▸` assistant | **+ success-tone notice (`✓ Loaded skill <name>`)** |
| `$secondary` | `yellow` | User label `You`, prompt `›`, thinking `●` | unchanged |
| `$error` | `red` | Error messages, `✗` | **+ error-tone notice (`✗ Skill '<name>' not found`)** |

| `$accent` | `blue` | Picker only (11-UI-SPEC §5) | unchanged — **blue stays picker-exclusive** |

### Accent reserved for (explicit — never "all interactive elements")

`$accent` blue usage is unchanged from 11-UI-SPEC §5: exactly three places, all inside the `/session` SessionPicker (picker border, cursor prefix `>`, cursor-row title). Blue is NOT used in the footer chip, the notices, or the InputBar.

### Color rules (tui-design, carried forward)

- Every color signal is paired with a symbol or weight: success notice = `✓` + green bold; error notice = `✗` + red bold; chip names = bold white over a dim label. No color-alone signaling.
- Semantic meaning only: green = success/affirmation, yellow = user/processing, red = error, blue = modal selection, cyan = header identity.

## 6. Component Design Contract

### 6.1 Footer chip line (footer.tsx — modified)

**Purpose:** Persistent, session-scoped "loaded skills" indicator on a dedicated row **above** the existing hint row (D-02). Renders only while at least one skill is loaded (D-01/D-09).

**States:**

| State | Visual |
|-------|--------|
| `loadedSkills.length === 0` | Chip row **not rendered** — footer is exactly today's hint row (zero-chrome empty state) |
| Skills loaded, fits | `Skill: demo-greeter · weather` — one line |
| Skills loaded, truncated | `Skill: demo-greeter · weather · +2 more` — kept names + dim hidden-count |

**Behavior:**
- Subscribes `const { loadedSkills } = useAgentStore()` — re-renders only on chip-relevant store changes (footer is cheap; no interval, no cascade risk).
- Row 1 (chip, conditional): `Skill:` label (dim) + space + names joined with ` · ` (bold white).
- Row 2 (hints): **unchanged** — exact existing hint set `[?] help  [/session] sessions  [/new] new chat  [Tab] panels  [q] quit` (11-UI-SPEC §6.5).
- Footer root becomes `flexDirection="column"` with the two rows; each row keeps `paddingX={1}`.

**Truncation algorithm (locked — the D-03 transparency floor):**
1. `W = terminalWidth - 4` (2 cells padding each side). Join all names with ` · `.
2. If joined length ≤ W → render all names.
3. Else drop trailing names one at a time until `kept + " · +N more"` fits, where N = count dropped; render the suffix `· +N more` in `dimColor`. The count is never hidden.
4. Hard floor: if even `Skill: +{N}` exceeds W (pathological < ~18-col terminal), hide the entire chip row (§9).

**Visual spec:**
```
Skill: demo-greeter · weather          ← row 1: dim "Skill:" + bold white names, " · " join
[?] help  [/session] sessions  ...      ← row 2: existing dim hints, unchanged
```

### 6.2 InputBar `/skill` intercept (app.tsx — extended)

Existing `useInput` intercept (app.tsx:41-79) gains two branches, mirroring `/session`/`/new` (16-CONTEXT D-05): exact match, handled inline, `setInput("")`, `return` — **never** reaches `submitPrompt`.

| Input (trimmed) | Action |
|-----------------|--------|
| `/skill` (exact, bare) | `addSkillNotice("Usage: /skill <name>")` — info tone (dim italic). Input cleared. **Not forwarded.** |
| `/skill <name>` (regex `^\/skill\s+(\S.*)$`) | `client.loadSkill(name)` → on ack: notice by `status` (§6.3 copy table); on RPC rejection: error-tone notice `Failed to load skill: {message}`. Input cleared. **Not forwarded.** |
| `/skills` | **NOT intercepted** — no `/skill*` prefix-greedy match. `/skills` falls through to `submitPrompt` exactly like any other unmatched text (v1.2 AUTH-02 listing is deferred; live behavior for unknown strings is unchanged). |
| anything else | `submitPrompt(trimmed)` — unchanged |

**Behavior notes:**
- Name argument is passed raw to `loadSkill`; case-insensitive win32 matching + canonical-name dedup are backend-side (12-CONTEXT D-06, 14-05) — the TUI does no name normalization.
- No `busy` flag is set during the load — the input stays focused and usable; the ack is fast (shared `load_skill()` path).
- The chip does **not** update from this RPC ack. It updates only when the backend's `skill_loaded` **notification** arrives (§6.4). On a real load both fire; on `already_loaded` only the ack fires (nothing changed — D-07).

### 6.3 `/skill` outcome notices (message.tsx + store — modified)

**Decision (locked from discretion):** **reuse the existing `notice` message role** — no dedicated role — extended with an optional `tone` field. `addError` is **not** used for `not_found` because it sets `status: "error"` (agent-store.ts:178-185), which would wrongly flip the app header into a red error state for a failed slash command. One new store action carries all three outcomes.

**Store action (agent-store.ts):** `addSkillNotice(text: string, tone?: "success" | "error")` — pushes `{ id, role: "notice", content: text, timestamp, tone }` to `conversation`. **Never touches `status`, `busy`, or `error`.**

**MessageCard (message.tsx:43-51) notice branch — locked rendering:**

| tone | Rendered copy (exact) | Style |
|------|----------------------|-------|
| `"success"` | `✓ Loaded skill <name>` | green, bold (`<Text color="green" bold>`) |
| `"error"` | `✗ Skill '<name>' not found` | red, bold (`<Text color="red" bold>`) |
| `undefined` (info) | `Skill '<name>' already loaded` · `Usage: /skill <name>` | existing notice style: `dimColor` + `italic` |

- `✓`/`✗` are the 09-UI-SPEC §6 glyphs already used by ToolCallIndicator — same vocabulary, no new glyphs.
- Copy strings are locked verbatim in §11; `<name>` is the **canonical name** returned in the RPC ack (`result.skill`), not the raw typed string.

### 6.4 `skill_loaded` notification → store (rpc-client.ts + types.ts — modified)

**Purpose:** notification-driven chip updates for BOTH activation paths (model-driven `read_skill` and user-driven `/skill`) — D-07/D-08. The notification drives the chip ONLY; it renders **no notice** (a model-driven load must not inject a stream message — ROADMAP criterion 4).

**types.ts additions:**
```ts
export interface SkillLoadedPayload { skill: string }   // canonical name (D-06: { skill } only)
// EventPayload union: add { type: "skill_loaded"; payload: SkillLoadedPayload }
// Message: add optional `tone?: "success" | "error"` (notice variants)
```

**rpc-client.ts `handleEvent` switch — new case:**
```ts
case "skill_loaded": {
  const p = payload as { skill: string }
  store.addLoadedSkill(p.skill)     // chip state only — no notice, no status, no busy
  break
}
```

**Store additions (agent-store.ts):**
- `loadedSkills: string[]` — canonical skill names, **load order preserved** (the order skills loaded, so the chip reads oldest→newest).
- `addLoadedSkill(name: string)` — append only if not already present (belt-and-suspenders; the backend dedups at the source, D-07).
- **Reset semantics (locked):** `loadedSkills: []` is set in **both** `resetConversation()` (the `/new` path, app.tsx:55) **and** `loadConversation()` (the session-switch path, session-picker.tsx → `loadConversation`, 11-UI-SPEC §6.3). This covers D-09's "clears on `/new` and session switch". No other reset point exists (startup is a fresh store; `setActiveSession` alone is not a reset).

**Backend touchpoints (non-visual — for executor awareness only, per 16-CONTEXT D-08):** `harness/events.py` new `SkillLoadedEvent` + `EVENT_SKILL_LOADED`; `harness/runtime.py` `load_skill` emits it **after** `add_skill_message` (runtime.py:212) and **only** for real loads — never on the `already loaded` early-return (:196) nor the cap refusal (:204-207); `backend/rpc/server.py` `_DOMAIN_TO_NOTIFICATION` (:53) + `_PAYLOAD_EXTRACTORS` (:115) + subscribe/unsubscribe; `backend/rpc/protocol.py` `NotificationType.skill_loaded` (:78). These are implementation-plumbing details outside this contract's visual scope.

## 7. Interaction Contract

### Keyboard & input

| Key | Context | Action |
|-----|---------|--------|
| `Enter` | Input bar, text = `/skill` (bare) | `Usage: /skill <name>` info notice; input cleared; no fall-through (D-05) |
| `Enter` | Input bar, text = `/skill <name>` | `loadSkill(name)`; outcome notice per §6.3; input cleared; no fall-through |
| `Enter` | Input bar, other text | `submitPrompt` (unchanged) |
| `Enter` | Input bar, text = `/skills` | **NOT intercepted** — falls through to `submitPrompt` (v1.2 AUTH-02 deferred) |
| `↑` / `↓` | Input bar | Input history (unchanged) |
| `q` | App (picker closed) | Quit (unchanged) |

### Feedback table

| Scenario | Indicator |
|----------|-----------|
| `/skill demo-greeter` succeeds | `✓ Loaded skill demo-greeter` green notice; chip row appears with `Skill: demo-greeter` (via notification) |
| `/skill demo-greeter` again | `Skill 'demo-greeter' already loaded` dim-italic notice; chip unchanged (no notification — D-07) |
| `/skill nope` (unknown) | `✗ Skill 'nope' not found` red notice; chip unchanged |
| Bare `/skill` | `Usage: /skill <name>` dim-italic notice; nothing sent |
| RPC failure (timeout/process) | `Failed to load skill: {message}` red notice |
| Model calls `read_skill` mid-turn | Chip gains the skill (via notification); **no notice, no stream message** |
| `/new` or session switch | Chip row disappears (`loadedSkills` cleared — D-09) |

## 9. Floor Pressure-Test (tui-design)

| Terminal width | Behavior |
|----------------|----------|
| ≥ 68 cols | Full layout (11-UI-SPEC §9 unchanged). Chip row renders when skills loaded; truncation via §6.1 algorithm if names overflow. |
| 40–67 cols | DatePanel hidden (existing floor, unchanged). Chip row renders above hints; truncation kicks in earlier (W shrinks). |
| ≥ ~18 cols | Chip row always renderable (either full names or `Skill: +N more`). |
| < ~18 cols | Chip row hidden entirely (hard floor §6.1 step 4); hint row unchanged; no structural collapse anywhere. |

Rule: the chip never wraps to a second row and never pushes the conversation below a usable height — it is a 1-row conditional that yields gracefully. No "terminal too small" screen is added.
